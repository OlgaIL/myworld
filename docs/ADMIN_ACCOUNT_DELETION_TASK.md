# ТЗ и промпт: удаление аккаунтов в админке

Согласованные ограничения, 7 октября 2026 года:
аккаунты с оплатами и административные аккаунты удалять нельзя.
Модель согласована: GPT-6.1 Sol / High. Работа запускается последовательно
после завершения задачи гостевого хранения в той же папке.

## Назначение

Ольга может из карточки пользователя удалить тестовый аккаунт без оплат,
его документы и связанные данные, затем повторить регистрацию с нуля.
Операция доступна только через существующую авторизацию администратора.

## Промпт для разработческого чата

Реализуй доработку админки Word2you по этому ТЗ.
Работай только в `C:\Users\olgak\PROJECTS\myworld`.
Прочитай `AGENTS.md`, `docs/ROADMAP.md`, этот файл и результаты завершённой
задачи гостевого хранения. Не начинай редактирование или тесты с общей БД,
пока предыдущий разработческий чат не закончил работу в этой папке.
Принимающий агент должен обеспечить последовательный запуск.

Сначала проверь `git status --short --branch` и staged diff. Сохрани все
существующие незакоммиченные изменения. Не создавай worktree, копии проекта,
новые серверы; не переключай Git-ветку, не используй reset/stash, не делай
commit/push. Не публикуй и не тестируй production. Не вызывай платные API
и не запускай других агентов. Проверки удаления проводи на искусственных
локальных аккаунтах и файлах, не удаляй существующие реальные данные.

### Поведение админки

- В карточке пользователя добавь действие «Удалить аккаунт».
- Для защищённых пользователей и пользователей с платежами покажи причину
  недоступности удаления. Защита должна выполняться на сервере независимо от UI.
- Перед удалением покажи ID, имя/email при наличии, число документов и ясное
  объяснение, что аккаунт, фото, тексты и заявки будут удалены. Подтверждение
  требует ввода ID удаляемого аккаунта; отмена ничего не меняет.
- Во время запроса исключи повторное нажатие. После успеха верни администратора
  в список пользователей, обнови список; ошибки показывай понятным текстом.

### Запреты

- В первой версии консервативно блокируй удаление при любой записи `payments`
  для пользователя, независимо от статуса, в том числе тестовой, pending,
  canceled или failed. Не удаляй платежи для обхода ограничения.
- Дополнительно проверь записи начислений, подтверждающие оплату, чтобы не
  удалить платившего пользователя при неполной связи истории.
- В проекте административный вход использует отдельные ADMIN_LOGIN/PASSWORD,
  а не роль строки users. Не считай отсутствие роли признаком безопасности.
- Предусмотри явный список защищённых ID пользовательских аккаунтов
  `ADMIN_PROTECTED_USER_IDS` в серверной конфигурации; ID для production задаёт
  Ольга. Не пытайся угадать их по имени или логину администратора.
- Если список защиты отсутствует или некорректен, удаление должно быть выключено
  с понятной причиной. Защити также текущий req.user, если он есть в админской
  сессии. UI удаления не позволяет снимать защиту.
- Сохрани existing requireAdmin и проверь защиту запроса от подделки из другого
  сайта согласно текущей схеме сессий. Прямой API-вызов не обходит ограничения.

### Удаление и данные

- Перед окончательным удалением в транзакции повторно проверь защиту, платежи
  и актуальное состояние аккаунта. Одновременное создание платежа не должно
  позволять каскадно удалить этот платёж: обеспечь защиту на уровне БД/блокировок,
  учитывая нынешний `payments.user_id ... on delete cascade`.
- Проверь все внешние ключи и связи users/photos, гостевой перенос, заявки,
  начисления, очередь Telegram и другие связанные данные. Не оставляй тексты
  или ссылки на удалённые документы без явного обоснования.
- Удаление строки и файлов согласуй так, чтобы при сбое БД не потерять файлы
  ещё существующего аккаунта, а при сбое файловой системы можно было повторить
  удаление. Используй устойчивую очередь очистки или другое обоснованное решение.
  Если файлы ещё очищаются, интерфейс не должен заявлять, что всё уже удалено.
- Удаляй только файлы удаляемого пользователя. Сохрани файлы, на которые
  ссылаются другие документы/гости, и не допускай выхода за uploads через пути
  из БД или симлинки. Учти старую общую папку и новую структуру guests/users.
- Не удаляй документы, которые ещё обрабатываются/переносятся. Для первой
  версии допустим отказ с просьбой дождаться завершения обработки.
- Старая пользовательская сессия не получает доступ после удаления аккаунта.
  Повторный вход создаёт новый аккаунт с обычными начальными правилами проекта,
  без восстановления старых документов или начислений.
- Не меняй историю существующих бэкапов. В документации поясни, что удалённые
  данные могут оставаться в резервных копиях до окончания срока их хранения.
- Журналируй результат и техническую причину отказа без секретов и текстов.
  Не расширяй задачу до удаления личных архивов по неактивности.

### Приёмка

Проверь локально:

1. Администратор удаляет искусственный аккаунт без оплат; исчезают его данные
   и файлы. Повторная регистрация создаёт новый аккаунт.
2. Любая запись платежа и оплаченные начисления блокируют удаление; записи
   и файлы сохраняются, в том числе при прямом обращении к API.
3. Защищённый аккаунт, текущий пользователь админской сессии и отсутствие
   корректной конфигурации защиты блокируют удаление.
4. Гость/обычный пользователь не могут удалять аккаунты через admin API.
5. Отмена, неверный ID подтверждения, повторный запрос и неизвестный ID
   обрабатываются безопасно и понятно.
6. Ошибка БД не приводит к потере файлов, ошибка удаления файла допускает
   повтор; чужие и совместно используемые файлы остаются целыми.
7. Параллельное создание платежа, обработка и перенос не обходят защиту.
8. Старая пользовательская сессия теряет доступ; список и карточка админки
   корректно обновляются. Проверь интерфейс на компьютере и узкой ширине.

### Отчёт принимающему агенту

Верни итоговую схему, точный список своих файлов, результаты проверок,
ограничения и команды для Ольги: конфигурация защищённых ID, миграции,
обновление кода, сборка клиента, перезапуск, проверка production и откат.
Обнови ROADMAP, не отмечая production-проверку завершённой.
Коммит/push и приёмку выполняет принимающий агент после проверки твоего отчёта.
