# Порядок заголовка заявления — проработка 19 ноября 2026

Цель: в заявлении с различимой шапкой получить порядок «шапка → заголовок
с подзаголовком → основной текст», сохранив весь текст и его значения.
Сначала оценить влияние на другие документы, как просила Ольга 18 ноября.
Рабочий код обработки в рамках этой проработки не менялся.

После согласования Ольги подготовлена изолированная реализация и локальная
страница «До» / «После». Обычная загрузка не изменена. Результаты и ограничения:
[STATEMENT_HEADING_LOCAL_2026_11_19.md](STATEMENT_HEADING_LOCAL_2026_11_19.md).

## Что установлено на сохранённом примере

Проверена локальная запись №693 и принадлежащий ей кэш Google OCR.
Хэш кэша совпадает с исходным изображением, сохранены 244 слова.
Текстовый OCR начинается с «Заявление», хотя координата этого слова y=871;
«Заявитель» расположен на y=196, «Госпошлина» — на y=806.
Геометрия правильно показывает шапку над заголовком.

В сохранённом оформлении первый блок — heading «Заявление», второй —
paragraph с полями шапки, третий — подзаголовок. Проблема есть в сохранённых
данных, не только в CSS. promoteDocumentTitle меняет тип блока на месте
и не переносит его. Локальное дополнение промпта от 15 ноября не является
алгоритмической гарантией порядка. Дата сохранённого примера — 15 ноября;
по одной этой записи нельзя доказать, что её повторно обрабатывали новым промптом.

Офлайн проверена возможность переставить первые два готовых блока без потери
блоков или изменения их текста. Это ручная проверка одного примера,
не готовый универсальный детектор. Артефакты исключены из Git:
`work/statement-order-review-2026-11-19/`.

## Предлагаемое решение

1. Отдельная проверка порядка после ответа форматтера с использованием уже
   сохранённых координат OCR. Дополнительный OCR или вызов модели не нужен.
2. Применять только к заявлению/жалобе/сходной форме с одновременно найденными
   заголовком и шапкой адресата/заявителя. Требуются однозначная привязка
   заголовка к координатам и несколько независимых признаков шапки выше него.
   Одних слов «Заявление», «адрес» или наличия банковских реквизитов недостаточно.
3. Переносить готовый заголовок и его подтверждённый подзаголовок после шапки.
   Не перестраивать содержимое полей и их принадлежность людям в этой задаче.
   Несколько возможных заголовков, неподтверждённое сопоставление или смешанный
   блок с основной частью — отказ от автоматической перестановки.
4. После перестановки формировать cleanText из тех же блоков, чтобы вкладки
   «Текст», «Оформленный» и копирование показывали один порядок. Исходный OCR
   сохраняется; corrections, таблицы, списки и ведущие нули не теряются.
5. Выполнять проверку в пределах одной страницы. Общий заголовок
   многостраничного документа и порядок страниц не менять.

## Риски и контрольные примеры до подключения

| Пример | Ожидаемое поведение |
| --- | --- |
| Заявление №693 с заголовком перед шапкой | Заголовок после шапки; подзаголовок рядом |
| Заявление/жалоба с правильным порядком | Полное отсутствие изменений |
| Банковская справка №694 | Заголовок перед банковскими полями допустим; не переносить |
| Учебная таблица №692, обычное письмо, рецепт | Не применять правило заявления |
| Упоминание заявления/адреса в основном тексте | Не считать шапкой и заголовком |
| Заголовок разбит на слова или OCR исказил буквы | Переносить только при проверяемом однозначном сопоставлении |
| Несколько заголовков, таблица в предполагаемой шапке, несколько колонок | При неоднозначности оставить исходный порядок |
| Нет координат / чужой кэш / хэш изображения не совпал | Не переставлять автоматически |
| Списки, таблицы, исправления и копирование | Все блоки/значения сохранены; повторное применение ничего не меняет |
| Несколько страниц | Исправление одной страницы не меняет соседние страницы |

Текущий банковский обработчик на заявлении №693 и учебной таблице №692
возвращает not_applicable, на справке №694 — review/4 группы. Это показывает
разделение нынешних веток; безопасность нового обработчика ещё нужно доказать
его собственными тестами. Прежде чем менять рабочую загрузку, подготовить
изолированную локальную пробу и проверить перечисленные случаи.

Старые документы автоматически не переписывать. Для исправления уже
сохранённого заявления отдельно решить применение к его существующим блокам
и проверенному кэшу, без новой платной обработки.
