# Многостраничные документы: проект первой версии

9 ноября 2026. Этап 1: изучение текущего кода и проектирование.
Схема и API ниже — проект, не применённая миграция. Продуктовый код не менялся.
Основа: [задача](MULTIPAGE_DOCUMENTS_TASK.md).

## Решения обсуждения

- Только авторизованные пользователи. Для гостей всё работает по-прежнему.
- При выборе нескольких фото по умолчанию **отдельные документы**.
- Объединять в архиве можно только одностраничные документы. Наличие хотя бы
  одного многостраничного блокирует всю операцию.
- Извлечение страницы и разделение сохраняют её изображение и все результаты.
- Последнее решение Ольги: **в первой версии общий вызов LLM не нужен**.
  Автоматическая сортировка и генерация общих метаданных откладываются.
  Это заменяет промежуточные решения об автоматической генерации/обновлении.
- Сборка, разборка и перестановка не вызывают LLM или OCR и не списывают обработки.
  При добавлении фото обрабатываются только новые фотографии.
- Повторное открытие/копирование/объединение не пересчитывает готовые результаты.
  Кеш общего анализа и история объединений этой версии не нужны.
- Уточнение Ольги после просмотра упрощённого макета: каждая страница сохраняет
  собственные нынешние вкладки «Текст», «Исходный (без замен)», «Оформленный»
  и остальные по действующим условиям. Добавляются номер страницы и копирование
  страницы/документа; общего переключателя вкладок вместо постраничных нет.

## Что проверено в существующем коде

| Область | Как устроена сейчас | Следствие для разработки |
| --- | --- | --- |
| Хранение | `photosRepository.js`: одна строка `photos` содержит фото, тексты, метаданные, статус, исправления и таблицы | Оставляем эту строку страницей, не переносим результаты в новый общий текст |
| Идентификаторы | `mapPhotoInfo()` отдаёт `id = filename`; клиент открывает `/documents/:documentName` по имени файла, а не по числовому ID БД | Разделяем `documentId` и `pageId`, сохраняем старый маршрут |
| Загрузка | `useCabinetUpload.js`: подготовка → `/api/upload` → обработка → обновление; цикл последовательный, при ошибке прерывается | Порядок задаём до обработки; сохраняем успешную часть и сведения о незагруженных файлах |
| Баланс | Успех обработки и `incrementUserRecordsProcessedTotalWithClient()` сохраняются в транзакции; расходы считаются на уровне фото | Объединение не вызывает этот код. Не связываем баланс с количеством карточек |
| Неполная обработка | `partialProcessingService.js`: `recognized` сохраняет OCR при сбое оформления, обработка не списана | Текст доступен, а повтор оформления относится к конкретной странице |
| Архив | `listPhotosByUser()` возвращает все фото; клиент фильтрует и показывает по 30 | Группируем до поиска/выбора/пагинации. Самостоятельную серверную пагинацию не добавляем в эту задачу |
| Текст | `DocumentTextVariants.jsx` выбирает исходный/улучшенный/оформленный вариант, учитывает исправления и сохранённые таблицы | Общее копирование собирает тот же результат, который видит пользователь |
| Зависимости | `recognition_improvement_requests`, `document_ocr_layouts`, `table_processing_attempts` ссылаются на `photos.id` | При объединении/извлечении ID страницы и связи не меняются |
| Гостевой перенос | `guestStorageService.js` вставляет `photos` напрямую, переносит OCR-layout и создаёт `guest_document_claims` | Этот путь тоже создаёт одностраничный контейнер в той же транзакции |
| Удаление | `photoDeletionService.js`: savepoint на каждое фото, долговечная очередь очистки файлов, защита заявок `in_review` | Savepoint нужен на весь документ, иначе возможно удаление части страниц |
| Конкуренция | `accountOperationLocks.js`: общие блокировки загрузки/OCR, эксклюзивная для удаления | Используем тот же порядок блокировок для структурных операций |
| Названия | Миграция 047: отдельный `display_title`, уникальность у владельца | Архивные названия переносим на уровень документа, данные страницы сохраняем |
| Статистика | `/api/me`, админка и исторические `documents_*_total` считают фотографии | Добавляем явное число документов; прежние счётчики не переписываем задним числом |

Проверены файлы в рабочей папке, включая текущие незакоммиченные изменения.
Доступ к production, внешние вызовы OCR/LLM и чтение содержимого личных документов
для этого анализа не выполнялись. `server/db/README.md` содержит старое описание
in-memory-хранения; выводы сделаны по действующим маршрутам и репозиториям.

## Поведение первой версии

Правило работы, уточнённое Ольгой 15 ноября: перед реализацией интерфейса
показываем и согласовываем макеты в существующем стиле Word2you. Новые экраны
и диалоги опираются на действующие компоненты; согласование требований
само по себе не является приёмкой их визуального исполнения.

Требование к структуре кода от Ольги, 15 ноября: учитывать последующий отдельный
рефакторинг, соблюдать действующую логику и соглашения проекта. Переиспользовать
обработку, доступ/списания и отображение страницы; операции над составом документа
держать в отдельном сервисе, маршруты — без дублирования бизнес-правил.
Общую подготовку текста для постраничного и общего копирования использовать
повторно. Не совмещать функцию с масштабной перестройкой проекта.

### Загрузка и порядок

1. Одно фото: прежняя загрузка, результат — одностраничный документ.
2. Несколько фото: до отправки диалог «Как загрузить фотографии?» с радиокнопками
   «Отдельные документы» (выбрана) / «Страницы одного документа».
   Миниатюры, количество фото и кнопка запуска. До нажатия ничего не отправляем.
3. В одном документе исходный порядок равен порядку файлов, показанному в диалоге.
   Не обещаем, что системный выбор файлов сохраняет порядок кликов пользователя.
4. Из архива: начальный порядок по `photos.created_at ASC, photos.id ASC`.
   Предпросмотр показывает его до объединения. Ручную перестановку можно сделать
   в предпросмотре или внутри готового документа.
5. «+ Добавить страницы» всегда добавляет фото в хвост, без вопроса о режиме.
6. Перестановка — отдельный режим: миниатюры, номер, перетаскивание и кнопки
   «Выше»/«Ниже». На телефоне — вертикальный список с теми же кнопками.
   Изменения локальны до «Сохранить порядок»; «Отмена» возвращает сохранённый.
   Ольга уточнила название входа в режим: «Изменить порядок страниц».

### Название, описание и рубрики

Согласованное с Ольгой правило без новых вызовов:

- По уточнению Ольги 18 ноября шапку берём из текущей первой страницы.
  Если эта страница ещё
  не обработана, временно «Документ» без выдуманного описания.
- При объединении готовых документов берём шапку первой страницы предпросмотра.
  Показываем это в предпросмотре. Название/описание не объявляем обобщением
  содержания всех страниц: LLM его не составляла.
- При смене первой страницы перестановкой или выделением название и аннотация
  обновляются. Добавление страниц в конец не меняет первую страницу и шапку.
  В API источником служит первая страница в текущем порядке; снимки создания
  в таблице documents сохранены для совместимости, но не перекрывают её данные.
  Дата в архиве остаётся прежней по отдельному согласованному правилу.
- Разделение и выделение используют собственные сохранённые метаданные страниц.
  Архивное имя получает свободный суффикс по существующему правилу 047.
- Уточнение Ольги 16 ноября: при чтении у каждой страницы показываем собственные
  название и короткую аннотацию. Названия совпадают с используемыми в перестановке.
  Общая шапка документа остаётся сверху один раз. Справа от названия страницы —
  «Страница N из M» и «Убрать из документа»; на телефоне под аннотацией.
  Это выделение в отдельную запись архива с пояснением в диалоге, не удаление.
  Уточнение 18 ноября: название и аннотацию первой страницы под общей шапкой
  не повторяем. Сохраняем у неё номер и действие; у остальных страниц шапки видны.
  Это изменение отображения, без изменения метаданных, порядка или текста копии.
- Общие рубрики/тема — из той же исходной страницы; теги для фильтрации —
  объединение сохранённых тегов страниц. Поиск учитывает все страницы.
- Служебные заголовки/краткие описания показываем отдельно от распознанного текста
  и не включаем в общую копию. Настоящие заголовки внутри текста не вырезаем.
  Нынешний `promoteDocumentTitle()` умеет добавлять заголовок из метаданных:
  для страниц внутри группы такое добавление отключаем, не удаляя исходные блоки.

Новый редактор названия/описания в эту версию не добавляется.

### Копирование

- Страницу копирует существующая иконка внутри текста/вкладки с нынешними
  вариантами и оформлением. Дополнительную нижнюю кнопку не добавляем.
- У каждой страницы собственные вкладки и собственный активный вариант.
  Переключение страницы 3 не переключает остальные страницы. Доступность вкладок
  «Исходный (без замен)», «Улучшенный», «Оформленный», «Таблицы» и скрытие
  очевидного дубля определяются нынешними правилами страницы, а не всей группы.
- Общая заметная кнопка «Скопировать всё» — справа от названия документа,
  на телефоне под ним. «Добавить страницы» — в строке даты/статуса/количества
  над названием. Привычный плавающий «+» внизу справа открывает тот же диалог.
  Перестановка и разделение остаются под общей шапкой.
- Правки макета 17 ноября: дата, статус, число страниц и добавление выровнены
  по центру строки. Число страниц — 12 px, как статус, полужирное по последней правке.
  «Добавить страницы» и «Скопировать всё» — белые с серым двойным контуром справа
  и снизу; общая копия — чёрный обычный текст и иконка 30 px. Одна и та же кнопка
  также в конце документа справа, на той же горизонтальной позиции. На согласовании.
- В архиве чекбоксы и панель групповых действий появляются только после «Выбрать».
  Отмена очищает выбор; пакетная загрузка остаётся только для авторизованных.
- Согласовано Ольгой 15 ноября: последовательно собрать активный
  вариант каждой страницы. Например, страница 1 — «Оформленный», страница 2 —
  «Исходный»: копируются именно эти выбранные варианты. Переключать все страницы
  или выбирать отдельный общий вариант для этого не требуется. Режим «Таблицы»
  копирует только таблицы соответствующей страницы при постраничном копировании.
  По уточнению 17 ноября перед общим копированием открытые «Таблицы» автоматически
  переключаем на доступный «Оформленный». Остальные вкладки не меняем.
  Диалог: «Скопируем содержимое всех открытых вкладок в буфер обмена» и
  «Проверьте открытые вкладки». Перечисляем номера переключённых страниц.
  Если «Оформленный» недоступен, предупреждаем, что копируются только таблицы;
  недоступную вкладку не выбираем. Можно вернуться к страницам или подтвердить.
  Между страницами — пустая строка; пояснение о служебных названиях с новой строки.
  Диалог добавления: «Новые фотографии добавятся в конец документа», затем
  «Обработка запускается только для новых фотографий», затем «Максимум — 25 страниц».
  Диалог выделения: отдельные строки о сохранении в архиве и порядке остальных
  страниц. Добавить сюда можно одностраничный документ из архива, без списаний;
  запрет объединения многостраничных подтверждён Ольгой 17 ноября.
- «Текст» сохраняет текущую семантику страницы: `originalCleanText` из заявки
  при его наличии, иначе действующий `cleanText`, иначе OCR. Ручной результат
  берём только в выбранном «Улучшенный»/«Оформленный», как в нынешнем компоненте.
  При исчезновении/недоступности активной вкладки сохраняем нынешний переход
  страницы к «Тексту», другие страницы не переключаем.
- «Оформленный» использует существующее формирование блоков и сохранённые таблицы,
  с теми же включёнными/отменёнными исправлениями. Доступность и запасное
  представление сохраняют текущую логику конкретной страницы.
- Выносим вычисление готового варианта из компонента в общую чистую функцию:
  отдельное и общее копирование используют один алгоритм, без повторной LLM.
- Страницы соединяем двумя переводами строки, без добавления «Страница N».
  Служебное название/описание в общий текст не добавляем; содержательные заголовки
  и таблицы сохраняем. Таблицы между страницами не склеиваем.
- HTML-копирование: один HTML-документ, последовательно добавленные блоки страниц;
  нельзя конкатенировать несколько готовых `<html>`/`<body>`.
- При сохранённых, но ещё не загруженных таблицах сначала получаем их через GET,
  затем даём кнопку готового копирования. GET не восстанавливает таблицы заново.
- Во время обработки общее копирование недоступно. При итоговой ошибке/странице
  без текста: «Текст есть у 4 из 5 страниц» и явная кнопка «Скопировать доступный
  текст». Не показываем сообщение об успешном копировании всего документа.
- Ошибка буфера отображается как ошибка, не как успех. Экспорт файла отложен.

### Выделение, разделение и удаление

- Выделение переносит существующую страницу в новый контейнер, без копии файла.
  Родительский ID остаётся у оставшихся страниц. Осталась одна — обычный вид.
- Разделение: первую страницу оставляем в исходном контейнере, для остальных
  создаём одностраничные. ID фотографий и результаты остаются прежними.
- У единственной страницы нет действий «Выделить»/«Разделить».
- Изнутри документа страницы не удаляем: только выделяем. Удаление документа
  из архива удаляет все его страницы после подтверждения их количества.
- При массовом удалении допустим частичный успех между документами. Внутри
  каждого документа удаляются все страницы или ни одна. Файлы очищаются
  после фиксации транзакции через существующую долговечную очередь.

## Модель данных

Выбран вариант **новый контейнер + отдельная таблица связей**. Не храним
массив ID в JSON и не превращаем первую `photos` в родителя остальных.
Прямая колонка родителя в `photos` тоже возможна, но таблица связей лучше
отделяет существующее содержимое и служебный порядок; лишняя связь не нужна
ни OCR, ни таблицам, ни заявкам на улучшение.

| Сущность | Поля проекта и ограничения |
| --- | --- |
| `documents` | `id uuid PK`, `user_id bigint NOT NULL FK users ON DELETE CASCADE`, `title`, `display_title`, `summary`, `category`, `section`, `topic`, `tags jsonb`, `metadata_source_photo_id bigint NULL`, `metadata_state pending/ready`, `metadata_frozen boolean`, `structure_version bigint NOT NULL DEFAULT 1`, `created_at`, `archive_at`, `updated_at` |
| `document_pages` | `photo_id bigint PK`, `user_id bigint NOT NULL`, `document_id uuid NOT NULL`, `position integer NOT NULL CHECK(position > 0)`, `attached_at` |
| `document_aliases` | `old_document_id uuid PK`, `user_id`, `anchor_photo_id bigint`; только маршрутизация ссылок после объединения, без истории составов |
| `document_upload_batches` | `id uuid PK` (ключ клиента), `user_id`, `mode separate/group/append`, `target_document_id uuid NULL`, `initial_structure_version`, `state active/completed/partial/cancelled/expired`, `created_at`, `lease_until` |
| `document_upload_items` | `(batch_id, item_id uuid) PK`, `ordinal integer`, имя/размер/MIME файла, `content_sha256 NULL`, `photo_id bigint NULL`, `state pending/stored/error/cancelled`, `error_code NULL`; `UNIQUE(batch_id, ordinal)` и уникальная непустая связь `photo_id` |
| `document_operations` | `(user_id, operation_id uuid) PK`, `kind`, `request_hash`, `result_json`, `created_at`; квитанция мутации для безопасного повтора |

Ограничения и инварианты:

- В `photos` не меняем существующие ID, `filename`, пути или текстовые поля.
- Новые служебные таблицы принадлежат аккаунту и удаляются вместе с ним.
  Закрытая загрузочная сессия не создаёт страницы заново после их удаления:
  повтор возвращает итог/состояние удаления, не выполняет старую команду повторно.
- У каждого сохранённого фото ровно одна связь `document_pages`. После миграции
  обеспечиваем это отложенным constraint-trigger при INSERT фото и удалении/
  переносе связи; проверка на COMMIT позволяет создать фото и связь в одной
  транзакции. Удалённое фото проверять не нужно.
- `UNIQUE(document_id, position) DEFERRABLE INITIALLY DEFERRED` позволяет
  переставлять позиции без временных конфликтов. После операции нормализуем
  позиции; при незавершённой загрузке допустимы пропуски, порядок — по position.
- Добавляем `UNIQUE(id, user_id)` для `photos` и `documents`. Составные FK
  `(photo_id, user_id)` и `(document_id, user_id)` в связях запрещают чужую
  страницу внутри документа даже при ошибке приложения.
- Связь на фото — `ON DELETE CASCADE`; удаление строки документа само по себе
  не удаляет изображения. Удалять документ можно только сервисом, который
  удаляет его страницы и ставит файлы в очередь. Deferred-проверка не разрешит
  оставить живые фотографии без контейнера.
- Источник шапки необязателен: после удаления исходной фотографии ссылка
  обнуляется, сам снимок метаданных остаётся. Владелец источника проверяется
  при назначении, включая сценарии выделения/объединения.
- Непустые контейнеры — правило сервиса плюс отложенная проверка при COMMIT.
  Создаём контейнер вместе с первым успешно сохранённым фото; пока файла нет,
  существует только загрузочная сессия. Нет карточки пустого документа.
- `display_title` уникален среди документов пользователя по `document_title_key`.
  Названия страниц остаются сохранёнными; распределение имён документов
  выполняет отдельный allocator с блокировкой владельца, аналогично 047.
- Кешей распознанного «общего текста», результатов сортировки и фоновых
  LLM-задач в этой схеме нет. Итоговый текст собирается из сохранённых страниц.

`archive_at` — дата для списка: у старого документа прежний `photos.created_at`,
при объединении максимальная дата выбранных страниц; выделение/разделение
возвращает дате карточки дату исходной фотографии. Перестановка и добавление
не поднимают документ в архиве. Эта политика согласована Ольгой 15 ноября.

## API и совместимость

Все новые маршруты используют `requireAuthenticatedUser`. UUID документа
отличаем от существующего публичного ID фотографии (имени файла).

| Маршрут проекта | Запрос / результат |
| --- | --- |
| `GET /api/documents` | `{documents: DocumentSummary[]}`; одна запись на контейнер: ID, шапка, `pageCount`, `coverPageId`, `structureVersion`, `archiveAt`, счётчики статусов и доступные действия; поисковые данные всех страниц |
| `GET /api/documents/:documentId` | `{document, pages[]}` по position; фото = существующий `mapPhotoInfo` + числовой `photoId` строкой и position. Общий ID не заменяет `filename` в старых page-API |
| `GET /api/document-location/:pageName` | По имени файла и владельцу возвращает текущие `documentId`, `pageId`, `position`; чужой/несуществующий объект — 404 |
| `POST /api/documents/merge` | `{operationId, sources:[{documentId, expectedVersion}], orderedPageIds[]}`; минимум 2 разных одностраничных, новая структура и удалённые из списка ID |
| `PUT /api/documents/:id/page-order` | `{operationId, expectedVersion, pageIds[]}`; точная перестановка всех страниц без повторов/потерь |
| `POST /api/documents/:id/extract` | `{operationId, expectedVersion, pageId}` → родитель и новый одностраничный документ |
| `POST /api/documents/:id/split` | `{operationId, expectedVersion}` → список получившихся одностраничных документов |
| `POST /api/documents/delete-batch` | `{operationId, documents:[{id, expectedVersion}]}` → `{deleted[], missing[], failed[], cleanupPending}` с результатами на уровне документа |
| `GET /api/document-operations/:operationId` | Квитанция структурной операции владельца: завершённый результат либо отсутствие; отсутствие не доказывает, что параллельный запрос завершился ошибкой, повтор безопасен с тем же ключом |
| `POST /api/document-uploads` | `{batchId, mode, targetDocumentId?, expectedVersion?, items:[{itemId, ordinal, name, size, mimeType}]}` → состояние загрузки и текущие ограничения |
| `PUT /api/document-uploads/:batchId/items/:itemId` | multipart `photo`; атомарно создаёт фото и связь, возвращает уже созданное при точном повторе; тот же ключ с другим содержимым — 409 |
| `GET /api/document-uploads/:batchId` | Сохранённые фото, позиции, ошибки и отсутствующие файлы; доступен только владельцу |
| `POST /api/document-uploads/:batchId/finish` | Закрывает загрузку; незагруженные файлы отмечаются, успешные страницы остаются |
| `POST /api/document-uploads/:batchId/cancel` | Останавливает будущие загрузки; уже сохранённые страницы не удаляются |

Структурные ответы содержат свежие версии затронутых документов.
Уточнение реализации 16 ноября: documents в ответе мутации — ссылки
`{id, structureVersion, pageCount}`, без распознанного содержимого. После
успеха/повтора клиент запрашивает актуальные страницы через GET. Такой же
компактный результат хранится в квитанции; удалённые тексты в ней не остаются.
Общие ошибки: 401 `UNAUTHORIZED`, 404 `DOCUMENT_NOT_FOUND`,
409 `DOCUMENT_VERSION_CONFLICT`, `DOCUMENT_BUSY`, `ACCOUNT_BUSY`,
`MULTIPAGE_MERGE_NOT_SUPPORTED`, `UPLOAD_BATCH_ACTIVE`,
422 `INVALID_PAGE_ORDER`, `DOCUMENT_PAGE_LIMIT`, `INVALID_SELECTION`.
Смешанный выбор с многостраничным документом возвращает именно
`MULTIPAGE_MERGE_NOT_SUPPORTED` без любых изменений.

Новый клиент открывает `/documents/d-<uuid>?page=<pageId>`.
Старый `/documents/<filename>` разрешает страницу через location API и
открывает её текущее место. `?view=tables` сохраняется. После объединения
прежний UUID удаляемого контейнера получает alias на его исходную страницу;
он разрешается через текущую связь страницы, поэтому не нужны цепочки
редиректов или история объединения. Удаление фотографии удаляет её aliases.

Операции OCR, исправлений, таблиц и заявок остаются на `/api/photos/:filename/...`.
`/api/upload` для старого одностраничного сценария создаёт контейнер и фото
вместе. Старое DELETE фото разрешено только для одностраничного контейнера;
для страницы многостраничного — 409 с предложением выделить страницу.
Старое пакетное DELETE заранее проверяет это для каждого переданного имени,
не удаляет внутренние страницы и не расширяет запрос на весь контейнер.

## Блокировки, повторы и баланс

- Структурные операции используют существующую эксклюзивную блокировку
  аккаунта; транзакция блокирует контейнеры в порядке ID, затем их страницы.
  Блокировки возвращаются до начала сетевого OCR; длинных транзакций вокруг
  внешнего API нет. Сетевой OCR держит нынешнюю shared account-блокировку.
- Загрузка порции держит логическое право добавления в выбранный документ
  через активную batch-запись. Между HTTP-запросами другой вкладке запрещены
  удаление/разделение/перестановка этого документа. Уже сохранённый текст читать
  можно. Завершение, отмена или истечение lease освобождает его.
- Новый файл получает позицию в порядке исходных slots, не по времени OCR.
  Обрыв браузера не удаляет сохранённые фото. Файлы, которые ещё не отправлены,
  сервер восстановить не может: просим выбрать их повторно, сопоставляем slots
  и проверяем содержимое, а не обещаем автоматическую загрузку после закрытия.
- Все мутации имеют `operationId`; результаты структурных операций хранятся
  в служебной таблице `document_operations(user_id, operation_id, kind,
  request_hash, result_json, created_at)` с уникальным ключом пользователя и
  операции. Запись результата — в той же транзакции, что изменение. Это защита
  повтора запроса, не пользовательская история объединений.
- Повтор ключа с другим телом отклоняется. При сетевом сбое клиент сначала
  проверяет результат/состояние, а не повторяет с новым ключом.
- Для OCR одной страницы нужен отдельный per-photo advisory-lock на время
  обработки, затем свежая проверка статуса. Нынешняя ранняя проверка
  `alreadyProcessed` до `processing` не защищает два одновременных запроса.
  Новый upload-flow не должен умножать вызовы или списания при повторе.
- Перед каждой обработкой перечитываем актуальный баланс. В первой версии
  сериализуем расходующие обработки аккаунта, чтобы две вкладки не использовали
  последний остаток одновременно. Не переопределяем тарифы или условия списания.
- После разрыва соединения сначала читаем сохранённый результат и проверяем
  блокировку незавершённой обработки. Если провайдер мог ответить, но результат
  не был сохранён, не делаем автоматический новый внешний вызов: показываем
  необходимость явного повтора. Блокировка исключает параллельный дубль, но
  не гарантирует восстановление ответа внешнего API после аварии процесса.
- Согласовано Ольгой 14 ноября: при нехватке остатка до старта весь выбор
  не запускаем, автоматически часть не обрабатываем. Сообщение с актуальными
  числами и согласованием слов: «1 фото — 1 обработка. Вы выбрали 5 фото,
  а доступно 3 обработки. Выберите не больше 3 фото или пополните баланс».
  Если баланс изменился в другой вкладке уже во время работы, останавливаем
  следующие обработки, сохраняем полученные страницы и явно показываем остаток.
- `recognized`/`error`/`no_text` не выдаём за успешную обработку; используем
  действующие правила. Повтор нужной страницы не затрагивает успешные соседние.
  Уточнение Ольги 14 ноября: повтор ошибки доступен внутри документа у нужной
  страницы. Показываем отдельно «Загружено: N, обработано: M» и отметку
  «Обработка не списана» по фактическому учёту. Объединение необработанных
  страниц и страниц с ошибками разрешено без запуска обработки; во время
  загрузки, обработки или проверки заявки объединение недоступно.
  15 ноября согласовано: заменить изображение загрузкой другого фото на то же
  место можно только при ошибке обработки или результате «Текст не найден»
  (фото без текста). Позиция сохраняется; для успешно обработанной страницы
  с текстом замена недоступна. В остальных случаях другое фото добавляется
  отдельной загрузкой, с обработкой по действующим правилам. Условия замены
  проверяет сервер; механизм замены и его совместимость со ссылками/данными
  страницы нужно включить в серверный этап до реализации этой операции.
- Существующие заявки `in_review` не теряются. Структурные действия при таком
  состоянии временно блокируются; это согласуется с нынешней защитой удаления.
  Создание заявки и запуск ревью тоже должны участвовать в том же протоколе,
  иначе однократной проверки флага недостаточно.

## Поиск, статусы и счётчики

15 ноября Ольга согласовала поиск по всем страницам с одной карточкой документа,
фильтр по тегам всех страниц и отдельный учёт документов/страниц. На карточке —
количество страниц; расход обработок по фотографиям по действующим правилам.
Объединение готовых страниц не расходует обработки.

- Поиск: общий заголовок и описание + метаданные, OCR/доступный текст любой
  страницы. Результат один на документ, с первой подходящей страницей для перехода.
  Фильтры и «Выбрать все найденные» работают по документам до пагинации.
- Для первой версии сохраняем клиентский поиск по загруженным данным архива.
  Не склеиваем все страницы в поле `cleanText`; сериализуем поисковые сведения
  отдельно. Получение полного содержимого документа не зависит от видимых 30 карточек.
- Обложка — первая страница текущего порядка. Число страниц — сохранённые
  фотографии; ожидаемые файлы считаются отдельно как прогресс загрузки.
- Статусы: «Загружаем 2 из 5», «Обрабатываем 3 из 5», «Готово»,
  «Готово частично: 4 из 5», «Нужна обработка», «Текст не найден».
  Конкретная ошибка/сбой таблиц остаётся у страницы и не скрывает текст соседних.
- `/api/me`: новые `documentsStored` (контейнеры) и `pagesStored` (фото).
  Старые `recordsStored` и `recordsProcessedTotal` сохраняют прежнюю семантику.
  Архив/навигация используют документы; доступ/пакеты — прежний учёт обработок.
- Исторические `documents_created_total/deleted_total` остаются счётчиками фото,
  не растут от сборки/разборки. В админке подписываем их как фотографии и
  добавляем текущее число документов. Статистику обработки страниц не переименовываем
  в число многостраничных документов и не пересчитываем старые отчёты.

## Предлагаемые технические пределы

15 ноября Ольга согласовала максимум 25 страниц на документ — при загрузке,
добавлении и объединении. Единая настройка, проверяется клиентом и сервером.
Остальные начальные технические настройки для локальной проверки:
не более 100 документов и 500 страниц на один запрос
пакетного удаления (клиент разбивает выбор по обоим пределам); lease загрузки
15 минут с продлением при запросах. Имена/размер файла не определяют дубликат:
повтор определяется ключом загрузки + SHA-256. Одинаковое фото с новым ключом
считаем намеренной новой загрузкой, автоматическую дедупликацию не добавляем.
Ограничения страницы файла прежние: JPEG/PNG/WEBP, до 10 MiB на сервере.
Большие документы и эти пределы проверить локально до включения функции.
